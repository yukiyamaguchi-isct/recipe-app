## このフェーズの分け方

**画面は外側から内側へ積む。**

Phase 2 は `lib/` の部品を先に揃えて上に積んだ。Phase 3 は取得が1関数で済むので、**画面を「まず1件が表示できる」状態にしてから、要素を1つずつ足す**形にした。こうすると各段階の終わりに必ず画面が動き、実機で見て判断できる。

| 層                 | 段階  | 何ができるようになるか                     |
| ------------------ | ----- | ------------------------------------------ |
| 取得（Repository） | 2     | 自分のレシピだけを1件取れる                |
| 画面の骨格         | 3     | `/recipes/<id>` が開き、開けない場合も出る |
| 中身               | 4〜5  | 手順と材料が読める                         |
| 絞り込み           | 6     | カテゴリで材料を絞れる                     |
| 移動               | 7〜8  | ヘッダーから移動でき、現在位置が分かる     |
| 改名（Req7）       | 9〜10 | タイトルをその場で変えられる               |
| 確認モード         | 11    | S-04c として表示できる                     |
| 接続               | 12    | 解析からそのまま確認画面に着地する         |
| 実測               | 13    | 実機と本番で通しで確認できている           |

**視覚仕様は各段階で当てる。** Phase 2 のように後からまとめて適用しない（design.md 6.1 が確定値の対応表）。

- **ローカルの作業ツリーが `origin/main` より4コミット遅れており、最初に読んだ `HANDOVER.md` は Phase 2 完了前の版だった。** 4.1 の内容が指示と食い違ったことで気づいた。`origin/feat/recipe-view` は `origin/main` と差分0で、`main` から切った直後の状態だった

- **大きな Markdown を Bash のヒアドキュメントで書いたら、161行目で無言のまま切れた。** ファイルは途中まで書かれ、残りがシェルのコマンドとして解釈されて `p: command not found` になった。**サイズの大きい文書はファイル書き込みツールを使う**

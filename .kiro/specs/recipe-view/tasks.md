## このフェーズの分け方

**画面は外側から内側へ積む。**

Phase 2 は `lib/` の部品を先に揃えて上に積んだ。Phase 3 は取得が1関数で済むので、**画面を「まず1件が表示できる」状態にしてから、要素を1つずつ足す**形にした。こうすると各段階の終わりに必ず画面が動き、実機で見て判断できる。

| 層                 | 段階  | 何ができるようになるか                     |
| ------------------ | ----- | ------------------------------------------ |
| 取得（Repository） | 2     | 自分のレシピだけを1件取れる                |
| 画面の骨格         | 3     | `/recipes/<id>` が開き、開けない場合も出る |
| 中身               | 4〜5  | 手順と材料が読める                         |
| 絞り込み           | 6     | カテゴリで材料を絞れる                     |
| 移動               | 7〜8  | ヘッダーから移動でき、現在位置が分かる     |
| 改名（Req7）       | 9〜10 | タイトルをその場で変えられる               |
| 確認モード         | 11    | S-04c として表示できる                     |
| 接続               | 12    | 解析からそのまま確認画面に着地する         |
| 実測               | 13    | 実機と本番で通しで確認できている           |

**視覚仕様は各段階で当てる。** Phase 2 のように後からまとめて適用しない（design.md 6.1 が確定値の対応表）。

### 実施時の記録

- **`not-found.tsx` の実際の差し込み位置は自動テストで踏めない。** 認可が先に効くため、未ログインでは `/login` に飛んでそこまで到達しない。**段階13（実測）に送った**

- **変えずに保存したら通信しない。** 無駄な往復と、`updatedAt` だけ動くのを避ける
- **クライアント側の検証はサーバーと同じ `lib/recipes/title.ts` を呼ぶ。** 通信を1往復省くためで、**サーバー側の検証を省いているわけではない**（あちらが最後の砦）
- **失敗しても編集をやめさせない。** 入力が消えると打ち直しになる。**親にも知らせない**ので、画面のタイトルとDBがズレることがない
- **⚠️ 段階7 のテストが1件古くなった。** 「ヘッダーにボタンは無い」という前提が `✎ 改題` の追加で崩れた。テストの意図（移動はリンクであること）に合わせて **`nav` の中に絞った**。**前提が変わったテストは、消さずに範囲を直す**
- **⚠️ 自分のテストの正規表現が誤っていた。** 「面を持たない」を `/bg-primary/` で見たら `hover:bg-primary-soft` にマッチした。`` は `-` でも境界になる。**variant（`:` を含むもの）を除いたクラスだけを見る**形に直した

### ✅ 実機確認（2026-08-24、ユーザー）

段階7・8・10 でまとめて確認した。**すべて問題なし。**

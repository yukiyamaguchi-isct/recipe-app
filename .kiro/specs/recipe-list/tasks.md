## このフェーズの分け方

**下から積む。** Phase 3 は取得が1関数で済んだので画面から作れたが、Phase 4 は**署名付きURLという新しい部品**が要る。ここが動かないとカードが成立しないので、**先に `lib/` を固めてから画面に乗せる。**

| 層                 | 段階  | 何ができるようになるか                      |
| ------------------ | ----- | ------------------------------------------- |
| 部品（S3・日付）   | 2〜3  | キーから表示できるURLが作れる。日付が出せる |
| 取得（Repository） | 4     | 自分のレシピだけを新しい順に一覧で取れる    |
| 画面の骨格         | 5     | `/` にカードが並ぶ                          |
| 空状態と導線       | 6〜7  | 0件でも迷わない。次の写真を撮りに行ける     |
| レスポンシブ       | 8     | PC で3列になる                              |
| 削除               | 9〜11 | 一覧からレシピを消せる（DB と S3 の両方）   |
| 持ち越しの解消     | 12    | S-04 から一覧へ戻れる（Phase 3 の Req7）    |
| 実測               | 13    | 実機と本番で通しで確認できている            |

**視覚仕様は各段階で当てる。** 後からまとめて適用しない（design.md 6.1 が確定値の対応表）。

- **下余白の値は資料から計算した。** FAB は下端 24px・高さ 64px なので**上端が 88px**。余白 16px を足して **104px**（`pb-26` = `--spacing` 4px × 26）

  - 並び順に頼っている以上、**`md:pb-26` を消すと md 以上でだけ隠れる**。消さないこと

- **⚠️ テストが設計の穴を1つ見つけた。** 「S3 の削除が失敗しても 200」というテストが**落ちた。**
  - 原因: ルートは `await deleteRecipeImage(...)` を**メインの try の中**で呼んでいたので、`deleteRecipeImage` が投げれば `errorResponse` が 500 に変換してしまう

  - → **ルート側に専用の try/catch を足して、構造として担保した。** 契約が破れたら 500 を返すのではなく、ログを残して 200 を返す
  - **これがまさに落とし穴 #8 の症状**（500 を見たユーザーが再試行して 404 を見る）。テストを先に書いていなければ、契約が破れた日に初めて発覚していた
- **`deleteMany` 一発にせず、取得 → 削除の2手にした。** 消した後では `imageKey` を取れず、**S3 の後片付けができなくなる**（落とし穴 #10）。順序をテストで固定した
- **取得と削除の両方の `where` に `userId` を入れ、両方をテストで固定した。** 「1箇所だけ緩める癖」を作らないため
- **取得できたのに削除件数が0のケース**（削除の二重送信など）も `null` に落とし、呼び出し側からは「見つからない」と同じ扱いにした

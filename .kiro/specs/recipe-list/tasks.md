## このフェーズの分け方

**下から積む。** Phase 3 は取得が1関数で済んだので画面から作れたが、Phase 4 は**署名付きURLという新しい部品**が要る。ここが動かないとカードが成立しないので、**先に `lib/` を固めてから画面に乗せる。**

| 層                 | 段階  | 何ができるようになるか                      |
| ------------------ | ----- | ------------------------------------------- |
| 部品（S3・日付）   | 2〜3  | キーから表示できるURLが作れる。日付が出せる |
| 取得（Repository） | 4     | 自分のレシピだけを新しい順に一覧で取れる    |
| 画面の骨格         | 5     | `/` にカードが並ぶ                          |
| 空状態と導線       | 6〜7  | 0件でも迷わない。次の写真を撮りに行ける     |
| レスポンシブ       | 8     | PC で3列になる                              |
| 削除               | 9〜11 | 一覧からレシピを消せる（DB と S3 の両方）   |
| 持ち越しの解消     | 12    | S-04 から一覧へ戻れる（Phase 3 の Req7）    |
| 実測               | 13    | 実機と本番で通しで確認できている            |

**視覚仕様は各段階で当てる。** 後からまとめて適用しない（design.md 6.1 が確定値の対応表）。

### 実施時の記録

- **`@aws-sdk/s3-request-presigner@3.1116.0` が入った。** 併存する `@aws-sdk/client-s3` は `3.1111.0` で**版が揃っていない**が、AWS SDK v3 はパッケージごとに版が進むので問題にならない。エクスポートは `S3RequestPresigner` と `getSignedUrl` の2つだけ
- **`expiresIn` の単位が「秒」であることを型定義の JSDoc で確認した**（`@smithy/types` の `RequestPresigningArguments` L56-60）。**ここを記憶で書いていたらミリ秒と取り違える余地があった**（落とし穴 #1）。ミスしてもエラーが出ず画像も表示されるため、**テストで `3600` を固定する**ことにした
- **`npm audit` が 3 high を報告するが、presigner とは無関係。** `prisma` → `@prisma/config` → `deepmerge-ts` の既存の依存で、**`npm audit fix --force` は `prisma@6.12.0` へのダウングレードを提案してくる。** Prisma 7 は確定事項なので**実行しない**（落とし穴 #26 として記録）
- **`HANDOVER.md` 4.2 は「Phase 4 の最初の仕事は `← 一覧` を戻すこと」としているが、段階12 に置いた。** リンク先の `/` は今も存在するので先頭でも動くが、**着地先が本物になってから実機で確認したい**ため。順序の変更はユーザーに報告済み
- **`app/recipes/[id]/not-found.tsx` のリンク先が既に `/` だった。** Phase 3 の申し送りは「S-02 に差し替える」だったが、**実際に必要なのはラベルの変更だけ**（design.md 6.6）
- **削除の順序を DB → S3 に決めた理由を design.md 5.3 に表で残した。** 逆にすると「画像の無いレシピがユーザーに残る」という**見える壊れ方**になる。Phase 2 の「S3 → 解析 → DB」と同じ考え方

# recipe-analysis（Phase 2）の要件定義

## 背景

`REQUIREMENTS.md` 4.2〜4.6 と `UI_DESIGN.md` S-03 に対応する。**MVPの中核**で、これまでで最も大きいフェーズ。

写真を選ぶ → リサイズ → S3 に保存 → Claude API で解析 → 材料を3分類して DB に保存、までを一本の同期処理で通す。表示（S-04）は Phase 3、一覧（S-02）は Phase 4。

## 前提（確定済み。蒸し返さない）

| 項目             | 決定                                                      | 出どころ                         |
| ---------------- | --------------------------------------------------------- | -------------------------------- |
| 解析方式         | **同期処理。ジョブキューを入れない**                      | `REQUIREMENTS.md` 9章            |
| 画像の正規化     | **長辺2576px / JPEG品質85**、クライアント＋サーバーの二重 | `REQUIREMENTS.md` 4.2            |
| 使用モデル       | **`claude-opus-5`**                                       | 2026-08-15 にユーザーが決定      |

| 離脱             | **MVPでは解析中の離脱を許さない**                         | `UI_DESIGN.md` S-03              |

## 要件

### Req1: 写真を1枚アップロードできる

- ユーザーはレシピページの写真を1枚選んでアップロードできる
- PC はドラッグ＆ドロップとクリック選択の両方、スマホは「カメラで撮る」を第一候補に置く
- 「JPEG / PNG・10MBまで」を画面に明示する
- 送信前にクライアント側で長辺2576px / JPEG品質85に正規化する（拡大はしない）

**受け入れ基準**

- [ ] PC でドラッグ＆ドロップとファイル選択の両方から画像を渡せる
- [ ] スマホでカメラ起動が第一候補として提示される
- [ ] 5〜10MB の写真を選ぶと、実際に送信されるのが1MB程度に縮んでいる（DevTools のネットワークタブで確認）
- [ ] 長辺2576px 未満の画像は拡大されない

### Req2: 対応外の入力を明確に弾く

- **HEIC は選択された時点で明示的なエラーを出す。** 無言で失敗させない
- 10MB を超えるファイルはサーバー側で拒否する
- JPEG / PNG 以外の形式を拒否する

**受け入れ基準**

- [ ] HEIC を選ぶと「対応していない形式」と分かるメッセージが出る
- [ ] 10MB 超のファイルを送ると 413 相当の明確なエラーが返る
- [ ] クライアント側の検証を迂回しても、サーバー側で同じ判定が働く

### Req3: 画像から材料と手順を構造化データとして取り出せる

- 材料名・分量（例: 玉ねぎ 200g）を取り出す
- 作り方を手順単位に分割して取り出す
- レシピのタイトルを取り出す
- 材料を「調味料 / 野菜 / その他」の3カテゴリに分類する。**分類は解析時に Claude が材料名から判定する**

**受け入れ基準**

- [ ] 実際の料理本の写真1枚から、材料・分量・手順・タイトルが取り出せる
- [ ] 材料がすべて3カテゴリのいずれかに割り当てられている
- [ ] 「少々」「適量」のような数値化できない分量が、そのままの文字列で保持される
- [ ] 手順が順序を保って分割されている

### Req4: 解析結果が確実に保存される

**`REQUIREMENTS.md` 4.6 の「確認画面を出す前に保存する」に対応。** 確認画面での離脱で、APIコストと30秒を払った結果を失わないため。

- 解析が成功した時点で、確認画面を表示する**前に** DB に保存する
- レシピは必ずログイン中のユーザーに紐づく
- 保存に失敗した場合、解析結果を失ったことがユーザーに分かる

**受け入れ基準**

- [ ] 解析直後に DB を見ると、確認画面を開く前にレコードが存在する
- [ ] 保存されたレシピの `userId` がログイン中のユーザーと一致する
- [ ] 他のユーザーのレシピが取得できる経路が存在しない

### Req5: 待ち時間の見せ方が破綻しない

解析は最大30秒かかる想定。**単一スピナーでは30秒は長すぎる**（`UI_DESIGN.md` S-03）。

- 進捗を段階で表示する（アップロード中 → 文字を読み取り中 → 材料を仕分け中）
- 解析中はこの画面に留める。バックグラウンド処理と完了通知は後続フェーズ

**受け入れ基準**

- [ ] アップロードから完了までの間、進捗の表示が少なくとも2回変わる
- [ ] 解析中に別画面へ遷移できない

### Req6: 失敗したときに次の行動が分かる

`REQUIREMENTS.md` 4.3 と `UI_DESIGN.md` S-03 に対応。

- 文字が読み取れなかった場合、撮り直しの具体的な指示を出す（例:「明るい場所で、ページ全体が入るように撮り直してください」）
- タイムアウト時は再試行の導線を出す
- 内部エラーの詳細（スタックトレース、APIキー等）を画面に出さない

**受け入れ基準**

- [ ] レシピが写っていない画像を送ると、撮り直しを促すメッセージが出る
- [ ] 各エラーで「原因」と「次にすること」の両方が読み取れる
- [ ] 英語のエラー画面やスタックトレースが出ない

### Req7: 保護されたエンドポイントとして成立する

**Phase 1 からの持ち越し**（`.kiro/specs/user-auth/requirements.md` Req4 の未確認2項目）。このフェーズで最初の保護付き Route Handler を作るため、ここで実装・検証する。

- Route Handler がセッションから `userId` を取得する。**クライアントから渡された `userId` を信用しない**
- 未ログインで叩くと 401 が返る
- レスポンス形式は `{ success, data, error }` に従う（`.kiro/steering/architecture.md`）

**受け入れ基準**

- [ ] 未ログインで解析エンドポイントを叩くと 401 が返る
- [ ] リクエストボディに他人の `userId` を入れても、その人のレシピにならない
- [ ] 成功・失敗のどちらも `{ success, data, error }` の形で返る

## 非機能要件

- **Vercel の実行時間内に収める。** `maxDuration = 60` と Anthropic SDK の timeout を保険として設定する
- **ローカルファイルシステムに永続データを書かない**
- 秘密情報（`ANTHROPIC_API_KEY`、AWS認証情報）は `.env` から読む
- PC・スマホの双方で崩れないレイアウトにする

## スコープ外

- **レシピの表示（S-04 / S-04c）** — Phase 3。このフェーズでは保存までを担保し、確認画面の中身は Phase 3 で作る
- **レシピ一覧（S-02）** — Phase 4
- **編集（S-05）** — Phase 5
- 複数枚の同時アップロード、PDF、動画
- バックグラウンド解析と完了通知
- 解析結果の再解析・やり直し
- ビジュアルデザインの適用（Phase 3 の直前に合流）

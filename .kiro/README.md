# .kiro

このプロジェクトの「記憶」を置く場所。Kiroフレームワーク（`kiro-personal-app-guide.md` 参照）に沿った構成。

```
.kiro/
├── steering/          # プロジェクト全体の設計方針。更新頻度は低い
│   ├── tech-stack.md
│   └── architecture.md
└── specs/             # 機能ごとの仕様。フェーズを開始するときに作る
    └── <feature>/
        ├── requirements.md  # 何が必要か
        ├── design.md        # どう実装するか
        └── tasks.md         # 何をやるか（チェックリスト）
```

## 上位文書との関係

| 文書                     | 役割                                                |
| ------------------------ | --------------------------------------------------- |
| `REQUIREMENTS.md`        | アプリ全体の要件。MVPスコープと後続フェーズの線引き |
| `UI_DESIGN.md`           | アプリ全体の画面設計                                |
| `.kiro/steering/`        | 実装方針。技術選定とアーキテクチャ                  |
| `.kiro/specs/<feature>/` | 機能単位の仕様。上3つを踏まえて具体化する           |

`specs/` は**フェーズ着手時に作る**。全機能分を先に書かない。仕様と実装がズレたら実装に合わせて仕様を更新する（Kiroの目的は「仕様が絶対」ではなく「プロジェクト記憶の同期」）。

## design.md の書き方

Phase 1 で、design.md の記述に**3件の誤り**が見つかった。3件とも「出典を書かなかった節」に集中していて、出典付きで書いた節からは1件も出なかった。以下はその反省から定めた規則。

### 1. 主張ごとに検証状態のラベルを付ける

| ラベル    | 意味                                                       | 実装時の扱い             |
| --------- | ---------------------------------------------------------- | ------------------------ |
| ✅ 実測   | 実際に動かして確認した。再現手順を併記する                 | そのまま信じてよい       |
| 📄 出典   | ライブラリのソースか公式ドキュメントで確認した。行番号付き | そのまま信じてよい       |
| ⚠️ 未検証 | 妥当だと考えているが確かめていない                         | **実装時に必ず確かめる** |

**ラベルの無い記述は「方針・判断」であって事実の主張ではない。事実を書くならラベルを付ける。**
言い換えると、**出典を書けない事実は書かない**。記憶で書いた API の形が、後で最も高くつく。

### 2. コードは import 行を含む完全な形で載せる

断片だけ載せると、実装時にそのまま貼って動かない。Phase 1 では `export { GET, POST } from "@/auth"` という1行だけを載せたせいで、`handlers` を経由する必要に気づけなかった。

ただし**見た目のクラス（Tailwind）は載せない**。`DESIGN.md` の合流で変わるため、design.md には構造と挙動だけを書く。

### 3. 「無いとどうなるか」を書く

やることの列挙より、**失敗モードとその見分け方**のほうが実装者を守る。

> ❌ `proxy.ts` に `export { auth as proxy }` を書く。
>
> ✅ `proxy.ts` に `export { auth as proxy }` を書く。
> **これだけでは何も保護されない。** next-auth の `handleAuth`（`lib/index.js` L146）は `let authorized = true` から始まり、`callbacks.authorized` が無ければ常に通す。
> **見分け方**: `/` に未ログインでアクセスして 307 が返ること。200 なら効いていない。

各フェーズの design.md には**「落とし穴の一覧」**の節を置き、実装中に踏んだもの・踏みかけたものを集める。新しく入る人がそこだけ先に読めるようにする。

### 4. 受け入れの確認手順を、外から観測できる形で書く

「未ログインならログイン画面に飛ぶ」では、実装者が自分のコードを見て判断してしまう。**コードを見ずに真偽が決まる基準**を書く。

> proxy あり → `/login?callbackUrl=...`（`callbackUrl` が付く）
> proxy なし → `/login`（付かない）
> → `callbackUrl` の有無で、どちらの層が効いているか判定できる

### 5. 画面の節は UI_DESIGN.md と役割を分ける

| 文書                              | 書くこと                                                         |
| --------------------------------- | ---------------------------------------------------------------- |
| `UI_DESIGN.md`                    | アプリ全体で変わらない**構造**（何をどこに置くか）               |
| `.kiro/specs/<feature>/design.md` | そのフェーズの**実装上の決定**（エラーコードと文言の対応表など） |

調べないと書けない情報（Phase 1 なら `@auth/core` のエラーコード一覧）は design.md に載せる。実装者が毎回ソースを読み直すのは無駄。

### 6. フェーズの終わりに「実施時の記録」を design.md へ還元する

tasks.md の「実施時の記録」が厚くなるのは、**本来 design.md に先に書いてあるべきだった内容が実装後に流れ込んでいる**兆候。フェーズ完了時に、次のような内容を design.md 本体へ移す。

- 設計時の記述が誤っていて直したもの
- 実装しないと分からなかった制約
- テストを書くときの前提（モックの必要性など）

tasks.md の記録自体は消さない（どの段階で何が分かったかの履歴として残す）。**design.md を「正」とし、tasks.md は作業ログとする。**

> **参考実装**: `.kiro/specs/user-auth/design.md` がこの規則に沿って書かれている。次のフェーズの design.md はこれを雛形にする。
